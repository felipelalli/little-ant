# 17. Corrections and superseded proposals

This section is normative. It prevents earlier, now-incorrect summaries from
being mistaken for current decisions.

| Earlier proposal or wording | Current decision |
|---|---|
| `seed`, `committed`, and `ready` remain as aliases or compatibility states. | Remove them from the 1.0 core. Natural-language compatibility belongs only to the operator. |
| The priority question is “Does X come before Y?” | Ask `Is "X" more important than "Y"?`; priority is a strict human importance order, not urgency, dependency, or execution sequence. |
| Priority needs an `equally important` answer. | Do not add equality to the strict order. Ordering skip may record `tie-break for me`, which delegates a provisional direction without asserting equal importance. |
| `?` is universal but hidden from menus. | Display `?` in every finite-choice loop as information/help without recording an answer or skip. |
| Phase or “derived readiness” sorts the human order. | Phase never sorts priority. It only informs provisional placement and dynamic selection. |
| The dependency DAG constrains priority sorting, forces blocker-before-blocked comparisons, and inserts a Brick only when it becomes unblocked. | Dependency and priority answer different questions. Every active Brick is positioned from birth; blocking affects eligibility and forecast pressure, never human importance or comparison validity. Unblocking preserves the existing position. |
| A Brick blocked by another Brick has no chance in the initial draw and contributes only a separately calculated blocker-pressure score. | Dependency blocking alone does not exclude an otherwise admitted active Brick from the initial attention draw. If drawn, its complete N-step blocker path resolves to the actionable endpoint; effective blocker pressure is derived from those paths rather than stored separately. |
| When a drawn Brick has several immediate blockers, always follow the first, highest, or otherwise deterministically preferred edge, or rank blocker branches with a separate formula. | Make a replay-deterministic weighted subdraw among admitted immediate blockers using the same focus-forecast weighting function, normalized locally over those branches. Every admitted branch retains positive probability, the chosen edge is recorded, and unchosen blockers remain inspectable and unresolved. |
| A Brick's stage combines maturity, execution, and completion. | Use independent `status`, optional `phase`, `work_state`, and exclusive current focus. |
| Every active Brick must receive a phase at capture and defaults to `spec`. | Phase is optional, lazy, behavior-applicable, and neutral when absent. |
| Restore the former seed glyph `🌱` as an `idea` phase marker. | The plant marker remains abandoned. It is not part of the 1.0 phase design. |
| Rename `spec` to `design`, or keep both as aliases. | `spec` remains the single canonical planning/specification phase and uses `📐` as its renderer marker. `design` is neither another value nor an alias. |
| Removed `kind` is fully replaced by phase as the Brick's work shape. | `kind` remains removed; phase describes a work phase, while generic interaction differences belong to versioned BrickBehavior. |
| Only one human WIP may exist. | Multiple WIPs are allowed; only current focus is exclusive. Default soft WIP limit is 3. |
| Starting a new Brick stops the previous WIP. | It removes focus from the previous Brick but leaves that Brick in WIP. |
| `estimate_hours` remains on Brick. | Remove hours from canonical Brick state. Store a discrete effort class and EffortProfile version; hours exist only in profile, planning, and observed-actual evidence. |
| Effort means a continuously updated remaining-work score from 0 to 1. | Effort is the total work for the current scope, represented by a discrete profile class. Remaining work is a conservative derived projection. |
| Effort needs a global pairwise order like priority. | There is no global effort list or public float. Assisted classification compares a Brick with high-confidence historical exemplars. |
| Progress or focus duration automatically lowers effort. | Progress never changes total effort. Only conservative progress evidence may lower derived remaining effort; focus duration alone is insufficient. |
| TaskJuggler export is necessarily active-leaf-only and parent roll-ups are rejected. | The earlier leaf-only inference is retracted. A confirmed non-overlapping planning cut determines which Little Ant nodes become effort-bearing TaskJuggler leaves for one plan. |
| Parent and child estimates are independent additive effort. | A parent estimate covers its total scope, including descendants. Decomposition coverage and a non-overlapping planning cut prevent double-counting. |
| Export chooses an optimistic, realistic, and pessimistic source estimate separately. | Each planning-cut item chooses one structural macro, and that macro expands to all three scenarios. |
| `PlanningScenario` must be a mutable core entity. | Each confirmed simulation produces an immutable planning manifest outside operational domain state. |
| Scope changes can be inferred semantically by the core and launch one bundled recalibration flow. | The core only raises mechanical `scope_review` suspicion. A human or operator confirms `scope_revised`; affected ordinary probes return through normal cooldown and aging. |
| `weight` remains a generic 0..1 user concept. | Remove ambiguous `weight`; use axis-specific derived scores and selection weights internal to forecast. |
| Impact is a public `impact_score` and `impact_confidence` pair. | Impact uses six expected-impact classes and four evidence-maturity levels. Internal reliability may be derived but is not a public decimal rating. |
| Impact means upside conditional on success. | Impact is expected impact: magnitude already accounts for the chance of occurrence. |
| Impact maturity is the probability of success. | Maturity describes evidence quality and directness; it is independent from the probability already reflected in expected impact. |
| Completing a validation activity automatically upgrades impact. | Purposeful validation is real Brick work. Its result becomes evidence, and a human or operator explicitly reassesses impact and maturity. |
| Validation work requires a special core entity or relationship. | Investigation is ordinary Brick work. The core may identify useful uncertainty, but method selection is external judgment and results return as Raw or attributed evidence before explicit reassessment. |
| Difficulty becomes another explicit rating. | Effort is the explicit workload rating; difficulty and friction are derived from behavior and context. |
| Raw is terminal after the first extraction. | Raw is durable and reusable, with orthogonal review and archive state. |
| Raw use consumes it or assigns it to one destination. | Raw-to-Brick and Raw-to-RawShelf uses are many-to-many and non-consuming. |
| Every external TODO must stop as pending Raw and pass through one mandatory extraction funnel before any work can exist. | External capture and semantic adoption are separate. Attributable source content is preserved as Raw, but a configured structured-task source may atomically create or reconcile the Raw and its positioned Brick or ListEntry. Unknown, mixed, and note-like sources remain pending Raw for triage. |
| TODOs from one provider should automatically share a provider-named RawShelf. | Provider, account, and external-container grouping is a derived source view. A confirmed ImportProfile may separately map that source to a semantic RawShelf, Brick parent, collection, or ListEntry owner. |
| An item deleted or missing upstream should be interpreted as done, dropped, or archived locally. | External work state and presence are independent. Only completion evidence may propose `done`; an authoritative deletion signal records removed presence, while ambiguous absence or access failure proves neither deletion nor completion. |
| Import reconciliation is one monolithic skill-owned “sync round.” | The core owns provider-neutral observations, identity, reconciliation, migration verification, cutover, and effects. Adapters translate provider mechanics, while the operator or powered-up REPL contributes only semantic judgment. Reviews are derived interactions, not meta-Bricks. |
| `erase-after-import` lets an Adapter delete each object as soon as its fetch succeeds. | Source cleanup is a destructive migration policy. The whole selected scope is previewed and verified first; then explicit approval releases item-scoped, auditable, resumable deletes. The Adapter executes them with a separately declared capability but cannot choose scope or bypass core verification. |
| Migration cutover deletes or detaches imported provenance. | Cutover retires the ImportProfile after every selected object has a resolved cleanup disposition. RawOrigins, snapshots, links, local work, stable external identities, and an immutable migration receipt remain inspectable as historical provenance. |
| `description`, source, attachment, and arbitrary Brick references should be unified in one open-ended `Artifact` bag. | Do not introduce a generic Artifact entity. A Brick owns canonical description directly; Raw owns durable material, one optional external origin, and immutable snapshots; typed RawLinks carry material roles; behavioral relationships remain first-class. |
| A Brick-owned `SourceLink` stores a locator, fingerprint, and mutable `diverged` flag independently from Raw. | External origin belongs to Raw. Check and refresh update origin observations and immutable snapshots; reconciliation is per RawLink and its reconciled snapshot; divergence is derived rather than stored as a boolean. |
| Inline text and bytes are external source kinds. | `inline_text` and `inline_blob` are capture or storage forms. Only externally backed Raw has a RawOrigin, and each Raw has at most one. Mirrors, forks, drafts, and published copies remain distinct Raw entities connected through provenance. |
| Every non-focusable list item should be Raw or another Brick. | A ListEntry is a lightweight occurrence owned by a batch Brick; it is neither Raw nor independently prioritized work. |
| A Brick or entry ID is the hash of its original title, and duplicate titles must be rejected globally. | Persisted entity identity is opaque and creation-derived. Titles may repeat; duplicate suspicion is scoped, explainable, and separate from identity. |
| A curated Party should use a readable immutable slug such as `bento_camargo` as its ID, with aliases preserving old slugs after rename. | Party identity is opaque and immutable. Mutable display labels and optional overlapping alternate names support rendering and candidate retrieval but never become global IDs, command aliases, or implicit text references. |
| Repeated titles need an appended date to avoid identity collision. | Creation time and semantic dates remain metadata. UI context and IDs disambiguate repeated titles without forced renaming. |
| A title should be destructively normalized for identity by trimming, lowercasing, and stripping emoji before hashing. | Identity never depends on title. Preserve verbatim input; apply only conservative Unicode and whitespace cleanup to the human-facing canonical English title; keep product-owned emoji in renderer metadata; and use multiple derived, non-identifying fingerprints for duplicate suspicion. |
| Every `@slug` substring in every free-text field is a global entity reference with implicit semantics. | `@...` is interface syntax only. Explicit selection creates a typed annotation to an opaque target ID on an annotation-capable field and text revision. Unconfirmed text stays literal, and behavioral relationships remain explicit. |
| `#shortid "title"` in prose is a soft Brick reference whose title acts as a checksum, while provider schemes form another globally parsed text namespace. | `#` opens Brick autocomplete and `@` opens Party autocomplete only on capable editing surfaces. Explicit selection creates a typed annotation to opaque identity. Ordinary URIs and provider-shaped strings remain literal; tracked external material is captured explicitly as Raw with RawOrigin and RawLink. |
| The same label such as `Milk` implies one global world object. | Each need is an occurrence. No global `Thing` or product catalog is introduced in 1.0. |
| Duplicate detection is exact title collision or silent content deduplication. | Use a ranked duplicate-suspicion pipeline over canonical English, scope, state, history, and attributed semantic evidence; never silently merge or discard input. |
| Maintenance uses grooming or sanity meta-Bricks. | Use derived proposals such as probes and reviews, not special meta-Bricks. |
| `next` returns only a Brick, or exposes one generic public `interaction` operation whose extensions may invent new actions. | `next` returns one member of a versioned closed set of core-defined focus-opportunity variants. Surfaces present the concrete domain action or question; extensions cannot add fundamental variants or commands. |
| An importance-comparison suggestion is headed `Compare importance` and always gives `Why` equal visual prominence. | Render the proposition itself as the primary `Next: Is … more important than … ?` prompt with directional yes/no/skip/help answers. Keep provenance structured and available through `?`; any compact reason summary is secondary. |
| A focus suggestion labels `y` as a screen-specific `focus` action, while approval labels it `approve`. | Ask a concrete yes/no proposition such as `Focus?` or `Send this follow-up?`. Preserve stable response meanings across surfaces: `y` confirms, `n` rejects, `d` completes, `s` skips without answering, and `?` explains or reveals context whenever each action is applicable. |
| Powered-up placement either replaces human importance or requires approval for every AI comparison. | The skill or powered-up adapter may submit attributed low-authority comparison evidence before prompting the user. The core performs provisional binary insertion, exposes the evidence in recap and history, and later seeks human validation when useful; dumb mode asks the comparison directly. |
| Approvals, overdue follow-ups, stale reviews, or another opportunity kind always run in a fixed lane before the focus lottery. | Every newly selectable opportunity kind enters the same weighted draw. Type alone grants no deterministic precedence. Only resuming an already pending interaction or active focus, and reporting a consistency failure that prevents a valid draw, happens first. |
| Forecast flattens every Brick and each of its applicable opportunities into one top-level candidate array, so a subject with several open questions or reviews receives several independent tickets. | Forecast is hierarchical. Each admitted attention subject participates once in its applicable scope; selection then makes a replay-deterministic weighted local subdraw among that subject's applicable opportunities. Project-like containers may introduce recursive child-scope draws according to BrickBehavior. “One lottery” rejects type precedence, not hierarchy. |
| Priority uncertainty is a stored boolean. | Use derived `priority_confidence`; “uncertain” is a projection threshold. |
| Contradictory comparison answers are rejected or immediately reorder by opaque weights. | Preserve the answer, mark the smallest affected segment provisional, and run local recalibration before atomic replacement. |
| Only the latest comparison matters. | Preserve full history, derive a current judgment, and weight newer evidence more strongly within authority rules. |
| The second “next list” is persisted. | Persist only the priority tree; derive forecast as a read-only probability distribution. |
| `digital` mode implies AI execution. | AI work is an explicit Delegation to an `ai_agent`; mode and executor are independent. |
| Product UI or data may remain in pt-BR. | All product commands, responses, shortcuts, data, docs, and canonical values are English. |
| The redesign should be called v2. | The target is Little Ant 1.0. |
| `due_at` plus a generic delay cost models time. | Use distinct `not_before`, `best_before`, and `deadline` semantics. |
| The REPL can wait until 1.5 or be a thin readline wrapper. | A full deterministic guided harness is required in 1.0 and must preserve canonical CLI semantics. |
| `:` opens the REPL command surface. | `/` opens a context-valid command palette in navigation mode; it remains literal during text editing. |
| The REPL is necessarily AI-free in every mode. | Dumb mode is AI-free; optional powered-up mode uses an explicitly configured stdin adapter and the same core-validated interaction protocol. |
| The operator skill must carry the full command catalog and deterministic workflows in prompt context. | Keep the skill thin. The core returns state-scoped valid actions, exact canonical commands, and on-demand help shared by REPL and skill. |
| Domain types such as grocery list, reading list, or feature backlog should become hard-coded core branches. | The core ships generic versioned BrickBehaviors; opinionated domain BrickTemplates are inspectable standard-library data. |
| Recurrence and habits may remain a post-1.0 backlog idea. | Minimal first-class standing work, recurring obligations, and practices belong to 1.0. |
| Every recurrence creates an overdue task when missed. | Obligations remain open and may become overdue; an applicable practice opportunity records an unfulfilled outcome and advances without creating infinite backlog. |
| Completing one Brick should run arbitrary `on_done` code that spawns or resurrects another Brick. | A restricted, inspectable opportunity trigger may release one opportunity on an existing standing target from one supported canonical source event. It executes no arbitrary script and changes no target lifecycle automatically. |
| A blocked or paused practice should continue accumulating failures. | Blocked or paused practice windows create no `not_done` outcome and do not break the streak. |
| Completing one run of standing work completes the Brick. | A run records one execution; the standing Brick persists and becomes derivatively dormant when currently ineligible. |
| Any change of method creates a successor, and superseding standing work automatically transfers its recurrence and streak. | Preserve one Brick when old and new executions belong to one honest history. Use a distinct successor when combining them would mislead; keep histories and streaks separate, and reconcile recurrence, triggers, dependencies, and placement explicitly. |
| Feeding the title of retired standing work automatically resurrects its former identity. | Duplicate suspicion may propose explicit reactivation or separate creation. Similarity never silently resurrects a terminal Brick. |
| Reading, watching, or otherwise consuming something requires a `consumable` Brick property. | Consumption is not another Brick axis. A generic `repeatable` BrickBehavior records executions and may schedule the same Brick again; a domain template such as `article_reading` supplies creation defaults. |
| A future revisit needs `opens_at`, `target_at`, `closes_at`, or another special date window. | Use the existing `not_before` meaning. A completion-triggered delay plus deterministic jitter chooses one future eligibility date without implying a target, deadline, or expiry. |
| Every auto-tick should print the same inline warning while a Brick is near or past `best_before` or `deadline`. | Date pressure remains continuously visible in forecast and status, while each meaningful threshold produces one deduplicated notice occurrence. Acknowledgment and notice snooze affect presentation only; unchanged conditions do not pollute every command result. |
| Location-aware work requires the core to read GPS coordinates or let a host silently wake, batch, and act on physical Bricks. | An adapter maps sensor data to a configured Place and submits an attributed, time-bounded observation. The core stores no required raw coordinates, changes only eligibility or forecast, and performs no silent action or notification. |
| Every repeated execution kills or completes one Brick and creates another. | A repeatable activity retains one Brick identity, one priority position, and execution history. Only recurrence periods that may remain independently unresolved, such as obligations, require separate occurrence Bricks. |
| Repeating a Brick requires another priority insertion. | The same repeatable Brick remains in the priority tree. `not_before` temporarily removes it from selection eligibility without changing its position. |
| An open-ended child container should be called a `queue`. | Use `collection`. Its child Bricks are ordered by human importance, never by insertion time or FIFO semantics. |
| `project` and `collection` differ only in presentation. | A project represents one finite parent outcome whose descendant scope contributes to completion. A collection is an open-ended set of independently focusable child Bricks and becomes dormant, not complete, when empty. |
| A useful template catalog requires hard-coded domain types in the core. | Ship a broad, versioned, inspectable standard template catalog as data. The core validates generic capabilities and expansion; it never branches on grocery, reading, sports, or software vocabulary. |
| Every broader behavior, template, importer, and enrichment must ship from the core repository or require a core release. | Define versioned Little Ant Packs. The core owns capabilities, schemas, validation, permissions, and replay; an open `little-ant-packs` repository distributes inspectable standard and community extensions without becoming domain authority. |
| Powered-up mode and the operator need a separate template-classification workflow. | All modes consume the same core-provided routing candidates and interaction envelope. AI may rank and fill a bounded proposal; rejection or dumb mode enters deterministic template browsing or a capability-guided custom builder. |
| The operator skill should hard-code one global shortcut grammar and channel details such as Telegram Markdown and keyboards. | The core interaction envelope supplies the currently valid actions, canonical commands, shortcuts, and help. The thin skill interprets language; first-party surfaces and typed UIAdapters render the same interaction for each channel without redefining semantics. |
| An interrupted question round needs a round or continuation Brick with a stored ordinal cursor such as “resume at 12 of 20.” | Confirmed answers are ordinary domain events. The core derives the next useful prompt from current state, retains replay information for pseudo-random choices, and never creates a continuation Brick. Exact progress is shown only when its denominator is genuinely known. |
| Partially typed text should be autosaved into the Brick description with a draft marker. | Unconfirmed text belongs to the surface checkpoint and has no domain authority. Only explicit confirmation updates canonical content; a future cross-surface draft operation would need its own explicit contract. |
| Binary snapshots are versioned “for free” because the data directory is a Git repository. | RawSnapshot history is defined by immutable domain events and content hashes. Snapshot bytes are part of the logical synchronized dataset, while Git or any other transport remains outside core semantics. |
| A replica may treat a referenced but absent blob as a valid metadata-only RawSnapshot. | Missing or hash-invalid bytes are an explicit incomplete or corrupted condition. A RawOrigin locator without captured bytes is not a RawSnapshot. |
| “Plain text is the source of truth” means the event log alone contains the entire dataset, or that databases are categorically forbidden. | The event log is authoritative for operational domain state and referenced canonical blobs are required dataset members. Databases and indexes may exist as disposable, rebuildable projections that never own unique canonical state. |
| Deep persistence design belongs in a new `docs/design.md`. | Keep the design record in the existing `spec/little-ant-1.0/` chapter structure. Promote only externally observable normative behavior into `spec/little-ant.allium`; do not introduce a parallel design-document destination. |
| A separate `la status --line` flag is needed for the canonical opening line. | `la status` has one compact canonical human rendering by default. Structured access returns that same `human` value with a sparse operational StatusSummary by default and an explicit complete projection when needed; REPL and other surfaces never introduce another status definition. |
| Every Brick mutator should echo the complete resulting Brick in JSON to avoid a follow-up `show`. | Return a compact typed postcondition with affected identity, relevant resulting state, revision, and semantic changes. Complete entity and audit projections remain explicit requests. |
| JSON can remove every `null`, empty collection, `false`, and zero through one generic cleanup rule. | Operational JSON is sparse, but omission is declared per field and projection. Meaningful false, zero, empty, and tri-state values remain explicit; absence never acquires one universal domain meaning. |
| Preparing a Brick requires a prioritized grooming meta-Brick with a fixed checklist for estimate, dependencies, decomposition, and placement. | Use a manually invocable or forecast-derived `brick_review` interaction over the target Brick. It asks only materially applicable questions, records ordinary domain events, and has no independent Brick lifecycle. Placement already exists from birth. |
| Direct completion from an early stage should fabricate promote, ready, or start transitions before recording done. | Removed stages have no synthetic path. `done` transitions any active Brick directly and preserves the honest absence of prior execution events, while still enforcing structural and BrickBehavior invariants. |
| `la done <raw>` should materialize a Brick automatically and then complete it. | Raw is material, not work, and has no `done`. Review, reopen, archive, and unarchive are explicit Raw operations; an operator may identify or propose real Brick work but the core never invents it to satisfy a command. |
| `already done` needs a separate command, completion kind, or skip reason. | It is ordinary `done` without prior start evidence, available by Brick reference and as a context-valid served action. No synthetic zero-duration start is recorded, and observed duration remains unknown. |
| External completion evidence may record the human's answer automatically. | External or AI evidence may propose the same canonical `done` operation with provenance, but it never gains human authority or silently finalizes work. |
| Closing the last child should automatically complete every ancestor, or make an empty parent ordinary work again. | A finite parent receives `review_parent`, with proposal strength derived from decomposition coverage and child outcomes. Confirmation may expose the next ancestor for a separate review, but never auto-completes it. An empty standing collection becomes dormant instead. |
| A generic `Plugin` type should provide arbitrary hooks for commands, lifecycle events, storage, ranking, or replay. | `Little Ant Pack` is only a distribution unit. Every `PackComponent` has one closed, typed contract; 1.0 has no generic Plugin entity, alias, hook, alternative ranking algorithm, event type, storage replacement, or replay execution. |
| Executable Pack components may choose any language, run in-process when official, or load unrestricted Lua and operating-system libraries. | Lua 5.4 is the only first-class executable Pack runtime in 1.0. Every official or community component runs in a fresh VM in the separate HsLua-based `lant-pack-runner`, under bounded host capabilities and resource limits. |
| Lua adapters should use ordinary HTTP libraries and receive provider tokens directly. | Pack code uses the host-owned `lant.http.request` contract. Exact hosts and credential slots are declared; a Little-Ant-owned credential broker injects authentication, and Lua never receives stored secrets or tokens. |
| Credentials should primarily come from a system keyring or arbitrary external credential command. | 1.0 uses a Little-Ant-owned encrypted local vault and memory agent. CredentialBindings are local deployment configuration, excluded from Packs, domain events, and ordinary dataset synchronization. |
| TaskJuggler-specific `.tjp` formatting belongs in the Haskell core or an implicitly privileged adapter. | The core owns effort semantics, planning cut, projection, validation, IDs, and immutable manifest. The standard Pack ships a Lua ReadOnlyExporter that owns `.tjp` serialization and serves as the public reference component. |
| Alternate presentation adapters may remain informal or post-1.0 integration code. | `UIAdapter` is a first-class typed executable PackComponent in 1.0. It renders the canonical InteractionEnvelope and maps channel input back to a canonical action ID and interaction revision without inventing semantics. |

Any earlier consolidation that states one-WIP exclusivity, Brick hours,
continuous public impact or effort scores, remaining effort as the primary
rating, additive parent/child effort, unconditional leaf-only export, mutable
planning scenarios, different macros per scenario, a post-1.0 REPL, or
non-English canonical product data is superseded.
